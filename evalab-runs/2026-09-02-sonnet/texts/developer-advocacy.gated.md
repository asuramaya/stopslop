Why we're investing in developer relations

We're hiring a developer relations team.

Most new customers over the past year read our docs, tried our SDK, or watched a conference talk before they spoke to sales. That path is the default now. If a developer can't figure out our API from the documentation alone, we lose them before a salesperson gets the chance.

Support tickets tell the same story. A large share of the questions we get aren't about bugs — they're about missing examples, unclear error messages, and gaps between what the docs describe and what the SDK does. Nobody owned those problems full time.

We want better documentation and real example code instead of stub snippets. We want engineers who spend time in our Discord and GitHub issues, answering questions as they come in. We want people who sit in on customer calls and bring back what they hear, because some of our best fixes started as an offhand comment from a developer stuck at 11pm.

This isn't a marketing hire. The team reports through engineering. Success looks like fewer support tickets, faster time from signup to a working first request, and docs developers trust enough to stop asking us questions we already answered.

If you've done this work before, we're hiring.
