The API's design philosophy centers on one rule: every endpoint returns the same shape whether it succeeds or fails. A response body always has `data` and `error` keys, so a client checks one field instead of branching on status codes, headers, and payload structure at once. Versioning lives in the URL path, not in headers, so you can read `/v3/orders` and know what you're calling without a docs lookup.

Idempotency keys are required on every write, not optional. A retried POST after a timeout creates one order, not two. This costs a header on every call and removes an entire class of duplicate-charge bugs. Pagination uses cursors, not offsets, because offsets break when rows are inserted mid-page; a cursor points at a record, so the page stays correct even as the underlying table changes. Rate limits are returned in response headers on every call, including successful ones, so a client can back off before hitting the wall instead of after.

None of these choices are exotic on their own, but together they favor a client that can be written once and trusted, over an API that's marginally easier to prototype against. Consistency costs a little verbosity up front and saves debugging later, and that trade holds across the whole API.
